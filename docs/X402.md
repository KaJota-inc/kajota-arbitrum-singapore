# x402 integration — gasless deposits

## The flow at a glance

```
+---------+                +---------------+                +---------------------+                +------------+
|  Agent  |  HTTP req      |  Kajota-Hub   |                | X402Deposit         |                | Cosell     |
| (buyer) | -------------> |  /pay/{list}  |                | Facilitator         |                | EscrowV2   |
+---------+                +---------------+                +---------------------+                +------------+
     |                            |                                    |                                  |
     |         402 + X-PAYMENT-REQUIRED (network, token, amount, recipient, nonce, deadline)              |
     |<---------------------------|                                    |                                  |
     |                            |                                    |                                  |
     |  sign EIP-3009 (TransferWithAuthorization)                       |                                  |
     |                            |                                    |                                  |
     |    HTTP req + X-PAYMENT: <base64 signature>                      |                                  |
     |--------------------------->|                                    |                                  |
     |                            |                                    |                                  |
     |                            |  relayDeposit(listingId, amount, buyer, validAfter, validBefore, nonce, v, r, s)
     |                            |----------------------------------->|                                  |
     |                            |                                    |  USDC.transferWithAuthorization  |
     |                            |                                    |  (pulls from buyer)              |
     |                            |                                    |  approve(escrowV2, amount)       |
     |                            |                                    |  escrowV2.deposit(listing, amt)  |
     |                            |                                    |--------------------------------->|
     |                            |                                    |                                  |
     |                            |                              depositId <-------------------------------|
     |                            |                                    |
     |                            |          200 OK + PAYMENT-RESPONSE (depositId, txHash)                |
     |<---------------------------|                                    |                                  |
```

## Why this shape

The agent never holds ETH. It signs one EIP-712 payload — a
`TransferWithAuthorization` over USDC, per Circle's canonical EIP-3009
spec — and hands the signature to any server. The server (Kajota-Hub,
a public facilitator, a keeper, or the counterparty itself) submits
the on-chain tx and pays gas. Same settlement primitive, no wallet
round-trip.

The facilitator is stateless w.r.t. funds. It never keeps USDC:

- **Relay path** — `USDC` flows buyer → facilitator → escrow in one
  transaction. The `PostRelayAssertionFailed` guard reverts if the token
  is fee-on-transfer and the amount that landed differs from what was
  authorized.
- **Refund path** — `escrow.refund(depositId)` sends USDC back to the
  facilitator (the recorded buyer of the escrow entry), and
  `refundToOriginalBuyer` forwards it to the address that originally
  signed the authorization. Anyone can trigger the refund; the funds
  always route to the recorded buyer.

## Facilitator responsibilities

| Concern | Where it's enforced |
|---|---|
| Signature validity | `MockUSDC.transferWithAuthorization` (or Circle's USDC on Arbitrum Sepolia) — same EIP-712 domain + type hash. |
| Replay prevention | Per-signer `nonce` map inside the USDC contract. |
| Time bounds | `validAfter` / `validBefore` in the auth; USDC rejects outside the window. |
| Fee-on-transfer safety | `PostRelayAssertionFailed` guard inside the facilitator. |
| Refund correctness | `_originalBuyerOf[depositId]` map; deletes on first refund to prevent double-drain. |

## Contract surface

```solidity
function relayDeposit(
    bytes32 listingId,
    uint256 amount,
    address buyer,
    uint256 validAfter,
    uint256 validBefore,
    bytes32 nonce,
    uint8 v, bytes32 r, bytes32 s
) external returns (bytes32 depositId);

function refundToOriginalBuyer(bytes32 depositId) external;

function originalBuyerOf(bytes32 depositId) external view returns (address);
```

Fully unit-tested against a MockUSDC that mirrors Circle's EIP-3009
domain byte-for-byte, so the same code path lands cleanly against real
USDC on Arbitrum Sepolia at
`0x75faf114eafb1BDbe2F0316DF893fd58CE46AA4d`.

## Client-side signing (viem sketch)

```ts
const signature = await walletClient.signTypedData({
  domain: {
    name: "USD Coin",
    version: "2",
    chainId,
    verifyingContract: usdcAddress,
  },
  types: {
    TransferWithAuthorization: [
      { name: "from", type: "address" },
      { name: "to", type: "address" },
      { name: "value", type: "uint256" },
      { name: "validAfter", type: "uint256" },
      { name: "validBefore", type: "uint256" },
      { name: "nonce", type: "bytes32" },
    ],
  },
  primaryType: "TransferWithAuthorization",
  message: { from, to: facilitatorAddress, value, validAfter, validBefore, nonce },
});
```

The `to` address in the authorization is the facilitator — the buyer is
authorizing USDC to move to the facilitator so the facilitator can then
forward into the escrow within the same tx.

## HTTP wrapping (server sketch)

```
GET /pay/{listingId}
→ 402 Payment Required
  PAYMENT-REQUIRED: <base64 JSON>
```

Body carries: chain (Arbitrum Sepolia), asset (USDC address), amount,
recipient (X402DepositFacilitator address), listingId, nonce, deadline.

```
GET /pay/{listingId}
X-PAYMENT: <base64 signed EIP-3009 authorization>
→ 200 OK
  PAYMENT-RESPONSE: <base64 { depositId, txHash }>
```

The server calls `relayDeposit(...)` on-chain and returns the settlement
metadata. From the agent's point of view, the payment step is one round
trip: 402 → sign → 200.
